- LATER THE SAME DAY — two new GENERIC viewer.html features, both OPT-IN from
  projects.js, currently committed for SOLAR RESTORATION ONLY (still to be
  propagated to the other 6 so the files stay in sync; they are inert without
  the projects.js keys, so propagating changes nothing for other clients):
    * `meta.autoLoadModels: true` — load the project's models/ folder on startup
      instead of leaving each model as an on-demand "Load" row.
    * `meta.clipToModel` — pull all six faces of the INITIAL crop box to the
      loaded model's bounding box, so the scan is trimmed to what the model
      covers. Forms: `true` (flush) | `<number>` (same margin on all six faces) |
      `{sides, z}` | `{x, y, z}`. Margins are METRES; POSITIVE leaves a gap
      outside the model, NEGATIVE crops further IN past the model's own extents.
      The result is intersected with the box's original cloud extents, so it can
      only ever crop IN, never grow past the scan. It runs from BOTH
      displayLoadedGroup() and just after the box is built, because the GLB fetch
      can finish either side of the point cloud's load callback (a latch stops it
      applying twice).
    * `meta.clipModelsToBoxes: false` — that project's models are drawn WHOLE and
      are not trimmed by the crop boxes until the user turns a model's ✂️ toggle
      on. REQUIRED alongside a negative clipToModel margin, because the box then
      cuts inside the model's own extents. Default stays TRUE, so every existing
      project (BDA St Joseph's model, Pomerleau's shoring, MurrayFranks' Dupont
      canopy) keeps clipping to its crop boxes exactly as before — all three new
      keys are per-project opt-ins with zero effect on anything that omits them.
  80 St Claire uses `autoLoadModels: true` + `clipToModel: {sides:-0.125, z:0}`
  + `clipModelsToBoxes: false` — the four side faces cut 125 mm INSIDE the model
  to shave the shaft walls off, top/bottom flush. Box 1.856 x 3.750 x 9.079 m
  (from 2.371 x 4.179 x 11.022).

# *** 2026-08-05 — ALL 7 VIEWERS: Tekla reference-model DXF export ***
#     (dev viewer = BDA; tested on 222 Jarvis; see memory
#      project_tekla_reference_model_dxf_2026_08_05 for full detail)
#############################################################################
- WHY: Tekla Structures cannot show a point cloud in a DRAWING view (documented
  limitation; the Open API does not expose the cloud renderer at all). It DOES
  draw REFERENCE MODELS in drawing views, and clips them by each view's own crop
  box + view depth. So one 3D DXF slab at true model coordinates serves every GA
  view, and the per-view toggle is just reference-model visibility. No C#
  Tekla.Structures.Drawing work is needed — Tekla does the trimming for free.
- Save/Export menu -> "Points -> Tekla DXF (mm, crosses)" (icon: crop), plus
  sliders for target cross count (25k-300k, default 100k) and cross size
  (2-20 mm, default 6). Requires a crop/focus box — aborts without one, because
  a whole-cloud Tekla DXF is never what is wanted.
- COORDINATES (the part that surprises people): IfcConvert maps IFC Z-up ->
  glTF Y-up and Tekla mm -> metres; the viewer's MODEL_X_ROTATION is the exact
  inverse, so a loaded GLB already sits at its true IFC/Tekla coordinates. That
  leaves only meta.modelOffset / meta.modelScale:
      Tekla_mm = (world - modelOffset) / modelScale * 1000
  Both are absent when the job is modelled directly in the scanner's own
  coordinate system (the normal case for this shop — everything stays in the
  X7/T100 frame), reducing it to metres -> mm. The DXF inserts into Tekla at
  origin 0,0,0 scale 1. Whatever offset was eyeballed to seat the GLB on the
  scan IS the scan->Tekla registration; no Tekla origin knowledge required.
- WHY CROSSES, NOT POINTS: Tekla renders bare DXF POINT entities unreliably in
  reference models. Each point becomes 2 LINE entities, and the arms lie along
  the crop box's TWO LONGEST LOCAL AXES — i.e. in the slab plane. World-XY arms
  would leave a VERTICAL section slab edge-on and effectively invisible.
- DENSITY: reference models stay usable around 50-150k entities (the old
  "Points -> 3D DXF" cap of 2M is fine for CAD, fatal here). Spacing is
  AUTO-SOLVED: seed voxel from the slice footprint (count scales ~1/s^2 since a
  scan is a surface, not a solid), deliberately overshoot the target, then
  coarsen by re-voxelling the array already in hand — so the octree is walked
  only ONCE. Solved spacing is reported in the toast.
- LAYERS: one per crop box, name uppercased from the box name (fallback
  CLOUD_1..n), plus <NAME>_EXTENT carrying the box mid-plane rectangle — a free
  calibration check and a visible slab extent on the sheet.
- SHARED REFACTOR (affects the LAS export too — regression-test it):
  _withForcedRegion(pcs, aabb, fn) was extracted out of exportSubScanLAS. It
  lifts the global + per-cloud point budgets, force-loads the region, runs fn,
  and ALWAYS restores the budgets. The old "Points -> 3D/2D DXF" path still uses
  extractPositions (currently-loaded LOD nodes only) and is left untouched.
- TEKLA-SIDE GOTCHA: reference models are typically OFF by default in drawing
  views. Double-click the view -> View Properties -> enable reference-object
  visibility. If still blank, check VIEW DEPTH first (a thin slab outside the
  view depth is clipped away entirely), then the view filter, then whether the
  drawing predates the reference model and needs updating.
- chrome.js buildSliderMenuItem now takes an optional item.fmt formatter (a
  plain toFixed(1) rendered the target count as "100000.0").

#############################################################################
- TOUCH WAS BROKEN because chrome.js caps touch Distance insertions at
  maxMarkers=2, so the FIRST tap auto-finishes the measurement and the 2nd point
  is produced by DRAGGING a stacked sphere out. The persistent-guide recorder was
  gated on `pendingMeasurement`, so on tablet/phone no guide was ever created ->
  no red reference dot / dashed connector, and the whole custom drag layer stayed
  inert (it bails on an empty _axisGuides).
- FIX: record the guide on the drag-out DROP (document mouseup, registered before
  the void-revert handler that clears _measDragObj); show the live guide during a
  reposition drag; store tipIdx/baseIdx on each guide instead of assuming the
  desktop 0/1 order (on touch both spheres start stacked, so either index can be
  the one grabbed).
- MULTI-POINT CHAINS (closes the PENDING item from 2026-07-29): _axisDimInfo()
  collects every guide belonging to a dimension and maps which point indices are
  axis-snapped TIPS. Dragging a free base rigid-translates the WHOLE chain, each
  point keeping its OWN axis coordinate (delta minus its axis component; full
  delta for never-snapped points) — consecutive segments may be on DIFFERENT
  axes. Tips are pinned and move only via their own red reference.
- NO MORE LOCKOUT: _axisReposBlockMsg deleted; grabbing a handle ADOPTS that
  segment's axis (_adoptAxisLock). The base point was never axis-snapped so it
  needs no lock and always moves freely in 3D. NOTE setAxisLock() TOGGLES when
  handed the axis already locked — guard on equality or it releases mid-drag.
- Reference points now highlight white on hover, like the base point.
- chrome.js findDraggableSphereAt: ties go to the LATER sphere. After a touch
  insertion both points sit at the same position (an exact tie), so strict `<`
  always grabbed the first one and the dragged-out point took the LOWER D#.
- PROPAGATION TRAPS LEARNED THIS ROUND:
  * `git apply` resolves patch paths against the REPO ROOT, not your cwd. Run
    from a client subdirectory and it prints "Skipped patch 'viewer.html'." and
    EXITS 0 — silently does nothing, and --check "passes" too. Use
    `git apply --directory="site/clients/<C>/"` from the repo root and ALWAYS
    verify with a grep for a string you just added.
  * The build tag is a single-quoted JS string; an apostrophe in the summary
    breaks the inline script in all 7 files at once. Syntax-check by extracting
    the inline <script> and running `node --check`.
  * WJ Properties carries uncommitted temporal work; its fix was staged without
    that work via `git hash-object -w` + `git update-index --cacheinfo`.
- NEW: RECOVERY.md in the repo root — how to rebuild this whole system on a new
  machine (accounts, R2 creds, tooling, workflow, what is NOT in git). Read it

# *** 2026-07-22 — ALL 7 VIEWERS: LAS multi-scan export fix + model offset ***
#############################################################################
- MULTI-SCAN LAS EXPORT FIX (BDA St Joseph has 2 scans: Main + Columns). The
  "Sub-scan -> LAS" export was dropping the SECONDARY cloud entirely. Two causes,
  both fixed in viewer.html (generic; propagated to all 7):
  * forceLoadAllNodes() only triggered loads ONCE. node.load() no-ops when the
    60-slot queue is full and a node's children are unknown until its hierarchy
    chunk loads, so a secondary cloud (only its root known) barely loaded. Now it
    RE-TRIGGERS every poll tick (function triggerPass) until the whole intersecting
    subtree is resident, with a ~5s stall guard. Preserves maxDepth/maxPoints
    (elevation) semantics.
  * exportSubScanLAS() now lifts each cloud's per-cloud pc.pointBudget to Infinity
    during the load (rebalanceScanBudgets caps them ~3M and the render loop would
    dispose forced nodes), restoring after.
  * _gatherLASPoints() now walks nodes ROUND-ROBIN across clouds (was cloud-by-
    cloud, primary first) so the 5M cap can't wipe out the second cloud; shared
    dedup set collapses overlap.
- PER-PROJECT MODEL OFFSET: displayLoadedGroup() reads meta.modelOffset {x,y,z}
  (world metres, Potree Z-up) to position a loaded GLB; defaults to (0,0,0). Set it
  to the NEGATIVE of the translation applied to the SCAN to align it, so panorama
  stations / second scan / marks stay put (we shift the MODEL, not the cloud).
- NEW MODEL: BDA St Joseph "Structural Model" (model.ifc -> models/model.glb via
  IfcConvert, 239 meshes). Uploaded to R2 bda/stjoseph/models/{model.glb,models.json}
  (discoverProjectModels reads it straight from R2 — loose glb/ifc gitignored).
  projects.js stjoseph.modelOffset = {x:-9.15, y:-32.16695, z:0} (scan was shifted
  +9150mm X / +32166.95mm Y). Build tag bumped to 2026-07-22 on all 7.

#############################################################################
# 4. DATA PIPELINE: raw scan -> served octree
#############################################################################
A) Inspect the LAS first (python + laspy): point count, RGB range (16-bit:
   0..65280 = 8-bit x256, so divide by 256 / >>8), native nearest-neighbor
   spacing, and bounds (to confirm a new HD/sub-scan aligns with the main scan).

B) Convert with PotreeConverter — RUN FROM POWERSHELL, from the converter dir,
   input as a POSITIONAL arg, use --attributes (not -a):
     cd 'C:\PotreeTools\PotreeConverter_1.7_windows_x64'
     .\PotreeConverter.exe "C:\...\<scan>.las" -o "C:\...\pointclouds\<id>" `
        -s 0.05 --scale 0.001 --attributes RGB INTENSITY --material RGB --overwrite
   - `-s` = ROOT spacing in metres (coarsest LOD; halves each deeper level).
     Conversion is LOSSLESS (octree cloud.js "points" == LAS point count — verify).
     Use FINER spacing to resolve fine features (cm GPR marks): 0.05 for big
     slabs (~30M pts), 0.01 for dense HD strips (~mm spacing). Default auto-
     spacing (~0.2-0.4) is too coarse for reading marks.
   - Convert to a *_v2 / temp dir, verify cloud.js, then swap folders; keep the
     old one in a _stale/ dir until confirmed, then delete.

C) (Optional but important for scanner color noise) COLOR-AWARE DESPECKLE.
   Symptom: scan looks crystal-clear in CloudCompare but speckled/washed-out in
   our viewer, white scan-line speckle burying colored (GPR) marks. CAUSE: the
   SOURCE colorization is noisy (~18% near-white points scattered through
   concrete); CloudCompare hides it by drawing ALL points dense, Potree shows a
   sparse LOD subset so each noisy point shows. The PotreeConverter does NOT
   average color — do not chase that. FIX = python despeckle that replaces only
   salt-and-pepper outliers while PROTECTING mark colours:
     - per point: 3D KNN median (k=12, scipy cKDTree, chunked query workers=-1)
     - replace only if dev=sum|RGB-median|>~85 AND not a protected colour
     - protect mask: (B>G+4) | (G>R+6) | (max-min>70)  [blue/green/saturated]
     - write back as 16-bit (value*256) so PotreeConverter handles it identically
   A PLAIN median (no protection) ERASES thin marks (they look like outliers vs
   white neighbours) and posterizes into blotches — that was a wrong turn.
   Helper scripts live (gitignored) at:
     site/clients/HRI/40 Larch 1/_despeckle.py  and  _inspect.py

D) Density when zoomed: native spacing may be ~1cm but the viewer can look
   2-3cm because of LOD throttling (NOT data loss). Levers in viewer.html:
   viewer.setPointBudget(...) and viewer.setMinNodeSize(20) (Potree default 30;
   lower = denser/deeper nodes load). The +/- keys are bound to point BUDGET,
   not size. When zoomed into a fully-loaded region you already see every point
   (== CloudCompare); remaining "CC is crisper" gap is render STYLE (point size
   slider / shape / EDL), and CC just draws all points always (no LOD).

# 6. PUSHING TO GITHUB (large data — MUST chunk)  *critical recipe*
#############################################################################
Repo: Enable-inc-git/enable_point_cloud_viewer over HTTPS. Netlify deploys
`main`. Convention here is to commit/push straight to main (that is the deploy).
Two real failure modes and their fixes:
  1. A single ~300MB push RESETS ("curl 55 Send failure: Connection was reset").
     FIX: split into multiple commits of ~80MB (48-110MB proven safe) and
     `git push` AFTER EACH — each push only uploads that commit's new objects.
  2. `git add file1 ... file400` -> "Argument list too long" (Git-Bash ARG_MAX),
     and it SILENTLY commits nothing. FIX: `git add` ONE file per call in a loop.
Working loop (bash), tally bytes, commit+push every ~80MB, verify each push:
  - first commit = code + manifests (cloud.js, sources.json, stations.json,
    projects.js, .gitignore) -> push (validates auth/connectivity)
  - then loop over `git ls-files -z --others --exclude-standard "<Project path>"`
    adding one file each, commit+push at ~80MB, final commit for remainder.
  - AFTER EACH PUSH verify `git rev-parse HEAD == git rev-parse origin/main`
    (a reset push can still exit 0 in a pipe — exit code is NOT proof).
  - End state: `git ls-files --others --exclude-standard "<path>" | wc -l` == 0.
A known-good script template was used for HRI 40 Larch 1 and 30 Weston Rd; see
the loop in §6 above — reproduce it as a .sh in the OS temp dir and run it in
the background (pushes can take minutes).
GITIGNORE already excludes: *.las, *.e57, *.scan, /potree/, each client's
panorama staging (images/ or HighResolution/), and HRI _*.py / _stale/.
NEVER commit: raw scans, *_project.bin scratch (can be many GB), tool checkouts.

# 9. SELECTED GOTCHAS
#############################################################################

  interior clickable — that was explicitly rejected.)
